# スマホ完結の動画編集PWA

スマホのブラウザだけで完結する、個人利用の動画編集ツール。
サーバーを持たず、処理はすべて端末内で行い、静的ホスティングだけで配信できる。

**ステップ1（書き出しの検証）は実機（iPhone Safari）で確認済み。** H.264/AACの
エンコード・デコードとも対応、書き出し・音ズレなし・保存まで動作した。
ステップ2（トリム・ピンチズーム）、ステップ3（dB表示）、
ステップ4（音声エフェクトと無音の自動カット）まで実装済み。

## 今できること

| できること | 操作 |
| --- | --- |
| mp4を開く | 「ファイルを開く」 |
| 再生位置でカット | 「ここでカット」／スペースキー |
| クリップを出力から外す・戻す | クリップをタップ（選択中のものをもう一度タップ） |
| クリップごとの速度 | ×0.5 / 0.75 / 1 / 1.25 / 1.5 / 2 の6ボタン |
| クリップの端をトリム | 選択中クリップの端（白い縦線のハンドル）をドラッグ。隣のクリップの境界までしか動かせない |
| タイムラインをズーム | ピンチイン・ピンチアウト（指の中間点の時刻を保ったままズーム＋パンする） |
| ズームを解除 | タイムラインをダブルタップ |
| 画質を選んで書き出す | 高画質 / 標準 / 軽量（1080pで12 / 6 / 3Mbps相当） |
| 保存 | 共有シート（iOSはここから写真アプリへ）／ダウンロード |
| 編集の途中保存 | localStorage に自動保存。同じ動画を開き直すと続きから |
| タイムラインの波形 | 開くと自動で解析（Web Worker）。dBスケール（0〜-60dB）、-3dB超は列を赤く強調、ピーク＋RMSを重ねて描く |
| 再生中のdBメーター | プレビュー右の縦バー。RMS＋ピークホールド（1.1秒）、-0.6dBでCLIPランプ点灯 |
| 音の仕上げ | トグル5つ（音量をそろえる／声をはっきりさせる／ノイズを減らす／音割れを防ぐ／出だしと終わりをなめらかに）。専門用語は出さず、ONで効く |
| 無音の自動カット | しきい値（-50 / -45 / -38dB）を0.6秒以上下回る「間」を外し、音のあるところだけのクリップに分ける。「元に戻す」付き |
| 字幕の自動生成 | 端末内のWhisperで下書きを作る（軽い=tiny / よく聞く=base の2択）。音声はどこにも送らない |
| 字幕の手直し | 再生位置に出ている1行だけを編集。始まり／終わりは0.1秒ずつ微調整、一覧から他の行へ飛べる |
| 字幕の見た目 | 配色6 × 書体4 の24プリセット＋位置3（上/中央/下）＋大きさ3。プレビューに重ねて確認できる |
| 字幕の焼き込み | 書き出すと映像に直接描き込む（字幕トラックは使わない。再生アプリによって出ないため） |

元ファイルは一切書き換えない。持っているのは「どこからどこまでを何倍速で再生するか」の
編集リストだけで、プレビューも書き出しもそれを読んで行う。

トリムは「選択中のクリップ自身の端」だけを動かせる。隣のクリップの領域には食い込めない
（両方の境界を一緒に動かす「リップル編集」はしない）ので、境界を詰めたいときは
両側のクリップをそれぞれ選び直して両方の端を動かす。

波形は音声トラックを区間ごとに分割デコードし、一定フレーム数ごとのピーク／RMSだけを
配列で保持する（全体をメモリに載せない）。ズームレベルが変わっても解析をやり直さず、
その配列を集約し直すだけで描く。dBメーターは別物で、`<video>` に挿したWeb Audioの
AnalyserNodeから再生中に毎フレーム読む。タイムラインの波形は左右チャンネルを合成した
1本だが、再生中のdBメーターはL/Rを2本のバーで別々に表示する。

音の仕上げは、プレビューではWeb Audioの標準ノード、書き出しでは同じ構成を組み直した
自前のDSP（`src/audio/dsp.js`）で処理する。書き出しはWeb Workerの中で走り、
Workerでは Web Audio API が使えないため。耳で確かめるのはプレビュー、
実際に出来上がるファイルを決めるのは書き出し側になる。

**接続順は仕様から1点だけ変えている。** 仕様は「…→リミッター→ゲイン→フェード」だが、
「音量をそろえる」のゲインは普通プラスの値になるため、リミッターの後ろに置くと
せっかく-1.5dBで抑えた音をまた押し上げてしまい、「音割れを防ぐ」というリミッター自身の
目的を打ち消す。そこでゲインだけ鎖の先頭へ移し、リミッターを最終段にしている。

字幕の時刻は **元動画の時刻** で持つ。文字起こしは元動画の音声に対して行うし、
あとからカットし直しても字幕が言葉に貼り付いたままになるため。書き出しでは
「このフレームは元動画の何秒目か」から引き当てて焼き込む。

まだ無いもの: 映像フィルター、マーカー、
PWA化（Service Worker）、ffmpeg.wasm フォールバック。これらはステップ6以降。

## 実機で確かめてほしいこと

WebCodecs は **https か localhost でしか動かない**ので、スマホで試すには
どこかに置く必要がある。いちばん手軽なのは Cloudflare Pages。

```
# Cloudflare Pages（ビルド不要・出力ディレクトリはリポジトリ直下）
#   Framework preset : None
#   Build command    : （空）
#   Output directory : /
```

開いたら、画面いちばん下の **「この端末の対応状況」** を見る。

1. `映像を書く（H.264エンコード）` が **対応** になっているか
2. 30秒くらいのmp4を開いて、カットと速度変更をして「書き出す」が通るか
3. 出来上がった動画をその場のプレビューで再生して、**音と映像がずれていないか**
4. 「保存・共有」から写真アプリに入れられるか
5. 書き出しに何秒かかったか（30秒の動画で何秒か）

うまくいかないときは「結果をコピー」でUser Agentと対応状況をコピーできる。
それを貼ってもらえれば原因を絞れる。

→ **iPhone Safari（iOS 18.7）で確認済み。** 判定は `ok`（H.264/AACとも対応）、
書き出し後の音ズレなし、ダウンロード保存も成功。

### 手元で動かす

```
npm install     # テストを走らせる場合のみ。アプリ本体はビルド不要
npm run dev     # http://localhost:5173
```

## テスト

```
npm test            # 下の2つを両方
npm run test:unit   # 編集リスト・リサンプラ・ビットレート・座標計算・字幕のデータと描画（Node）
npm run test:browser # 書き出し・タイムライン操作・波形解析・音の仕上げ・字幕（ヘッドレスChromium）
npm run test:transcribe # 文字起こしを最後まで（モデル83MBを一度落としてオフラインで実行）
```

`test:browser` は、1秒ごとに色が変わり秒ごとに音量も変わる12秒のテスト動画を
ブラウザ内で作り、3つの観点で確かめる。

1. カット・除外・速度変更を指定して書き出し、**出来上がった動画をデコードし直して
   「出力の何秒目に元動画の何秒目のフレームが来ているか」を色で確かめる。**
   音声と映像の長さのずれも見る。
2. タイムラインに実際の PointerEvent（タップ・ドラッグ・2本指ピンチ・ダブルタップ）を
   送り、シーク・ズーム・トリムが正しく発火するか（`test/timeline-interaction.js`）。
3. 音声を解析し、テスト動画の「大きい→標準→小さい→無音」の4区間それぞれで
   検出したdBが理論値に近いか、-3dBを超える区間だけが「音割れ危険」判定になるか
   （`test/waveform-analysis.js`）。
4. 音の仕上げをONにして書き出し、**出来上がったmp4をデコードし直して**
   リミッターが上限で止めているか、音量をそろえるとピークが-3dBに寄るか、
   フェードで頭と尻が絞れているか、無音カットで実際に短くなるか
   （`test/audio-effects.js`）。
5. 字幕を付けて書き出し、**出来上がったmp4のピクセルを読んで** 字幕が出ている
   時間にだけ文字が乗っているか、位置の指定どおりか、カットしても言葉についていくか、
   縦撮り（回転メタデータ付き）でも横倒しにならないかを確かめる
   （`test/subtitle-burn.js`）。字幕パネルの操作は合成クリックで別に検証する
   （`test/subtitle-panel.js`）。
6. 文字起こしのライブラリを正しいURL（`+esm`）から読んでいるか、Whisperに渡す音声が
   16kHzモノラルで正しく取り出せているか、WebGPUで落ちたときWASMでやり直せるか
   （`test/transcribe-library.js`）。
7. 落ちたあとの復帰 — 作業記録が残るか・間引きが効くか、動画をIndexedDBに入れて
   同じ中身のまま取り出せるか（`test/recovery.js`）。

`npm test` には入れていないが、`npm run test:transcribe` でモデルを一度落として
**文字起こしを最後まで走らせる**検証もできる（以降はオフラインで動く）。
CIに83MBは置けないが、ここでしか見つからない不具合が実際に2件あった。
経緯は `test/offline-transcribe/run.mjs` の冒頭に書いてある。

ヘッドレスChromiumはオープンソースビルドなので H.264 / AAC を持たない。
そのためテストだけは同じmp4コンテナのまま VP9 / Opus に差し替えて走らせている
（`runExport` の `codecs` 引数）。**つまり「パイプラインの論理」はCIで担保できるが、
「H.264/AACが実際に通るか」は実機でしか確認できない。** ステップ1でその点は
実機（iPhone Safari）で確認済み。

### 編集データ形式

これだけを保持し、localStorage に入れる。`id` と `enabled` は
UIがクリップを指すため／「除外しても削除はしない」ために足した2つ。

```json
{
  "source": "IMG_0431.mp4",
  "clips": [
    { "id": "c1", "in": 0.0, "out": 12.4, "speed": 1, "enabled": true,
      "filter": { "brightness": 1.05, "contrast": 1.15, "saturation": 1.3, "hue": -8, "vignette": 0 } },
    { "id": "c2", "in": 18.9, "out": 47.2, "speed": 1.5, "enabled": true, "filter": null }
  ],
  "audio": {
    "normalize": true, "normalizeGainDb": 4.2,
    "clarity": true,
    "highpassHz": 110,
    "limiterDb": -1.5,
    "fade": true
  },
  "subtitles": [
    { "id": "s1", "start": 1.2, "end": 3.0, "text": "こんにちは" }
  ],
  "subtitleStyle": { "preset": "white-gothic-bold", "position": "bottom", "size": "medium" },
  "markers": [ { "t": 24.0, "label": "要確認" } ]
}
```

`audio` は仕様の3つ（`normalizeGainDb` / `highpassHz` / `limiterDb`）をそのまま残しつつ、
数値を持たないトグル（声をはっきりさせる・出だしと終わりをなめらかに）のON/OFFを足してある。
`highpassHz: 0` と `limiterDb: null` がそれぞれ「ノイズを減らす」「音割れを防ぐ」のOFFを表す。
`normalizeGainDb` は波形から自動計算して入る値なので、画面から直接は触らない。

`subtitles` の `start` / `end` は **元動画の時刻**。出力側の時刻で持つと、
カットし直すたびに字幕を貼り直さないといけなくなる。

`filter` と `markers` はまだ読み書きしないが、後のステップでそのまま使えるよう
場所だけ確保してある。

### 当初の技術構成からの変更点

書き出しに mp4-muxer + mp4box.js を使う想定だったが、**mp4-muxer は作者自身が
非推奨とし、後継の Mediabunny へ移行するよう案内している。**
Mediabunny は同じ作者による後継で、mux と demux の両方を担当するため
mp4box.js も不要になる。加えて、

- ファイルを `Blob.slice()` で遅延読み込みする（mp4box.js は解析前に全体を
  メモリへ載せる必要があり、30分のスマホ動画ではタブが落ちる）
- `EncodedPacketSink` があるので、後のステップで「フィルターも速度変更もない
  クリップを再エンコードせず通す」無劣化パススルーを素直に実装できる

という2点が、長尺対応とメモリの要件に直接効く。詳細は `vendor/README.md`。

### 現時点で残している既知の課題

- **書き出し結果をメモリ上に一度組み立てている**（`BufferTarget`）。30秒なら問題ないが、
  長尺では `StreamTarget` + File System Access へ切り替える。フレーム自体は
  すでに逐次処理なので、差し替えるのは出力先だけ。
- **全クリップを再エンコードしている。** 無劣化パススルーはステップ6で入れる。
- **WebCodecsが無い端末のフォールバック（ffmpeg.wasm）が未実装。** いまは
  「対応状況」に理由を出して書き出しボタンを止めるところまで。
- **トリムは選択中クリップの端だけを動かせる。** 隣のクリップの端を同時に動かす
  「リップル編集」はしない（データ上は各クリップが独立して in/out を持つ設計のため）。
  境界を詰めたいときは両側をそれぞれ選び直してトリムする。
- **タイムラインの波形は左右チャンネルを合成した1本。** ステレオ感を見たい場合は
  再生中のdBメーター（L/Rを別バーで表示）の方を見る。
- **波形は毎フレーム、画面の列ごとに集約し直して描いている。** 長尺で極端に
  ズームアウトしたときの負荷はステップ9の負荷試験で確認する。
- **プレビューと書き出しでエフェクトの実装が別。** 数値（しきい値や周波数）は
  `EFFECT_PARAMS` で共有しているが、コンプレッサーの内部挙動はブラウザ実装と
  自前実装で完全一致はしない。最終的な音を決めるのは書き出し側。
- **プレビューにフェードは入れていない。** 書き出したファイルの頭と尻の話なので、
  プレビュー再生では省いている。
- **無音の自動カットはクリップ一覧を作り直す。** 速度や除外の指定は消えるので、
  直後だけ「元に戻す」で戻せるようにしてある。
- **自動文字起こしは、手で直した字幕も含めて置き換える。** 下書きを作る前に手で
  直すことは無いはずなので割り切っている。
- **字幕は同時に1行だけ。** 重なった字幕があっても、先に始まったほうだけを描く。
- **文字起こしの精度は端末とモデル次第。** 固有名詞や早口は外す。下書きとして使い、
  一覧から順に直していく前提の作り。無音部分の幻聴は音量で落としているが、
  雑音の上に出たものは残ることがある。
- **文字起こしは時間がかかる。** 手元のPC（WASM・tiny）で12秒の動画に5〜9秒。
  スマホはこれより遅い。進捗に「残り約N分」を出しているので、それを見て待つ。
- **大きいモデル（base）は端末によってはメモリが足りない。** 既定を小さいほう（tiny）に
  してあるが、それでも落ちる端末はありうる。落ちた場合は次の起動時に
  「前回ここで止まった」と出るので、それを見て判断する。
- **WebGPUは使っていない。** 速いが実機で落ちたため。CPU（WASM）だけで回している。
- **字幕を入れると書き出しが遅くなる。** 全フレームをCanvasに通すため。
  字幕が無いときは従来どおり素通しなので、速度は変わらない。
### 字幕まわりの設計判断

**焼き込み（映像に直接描く）を選んだ理由。** mp4には字幕トラックを入れる仕組みがあるが、
出るか出ないかは再生アプリ任せで、iOSの写真アプリやSNSに上げたときに消える。
「作ったものがそのまま見える」ことを優先して、映像のピクセルに描き込む。

**字幕があるときは全フレームをCanvasに通す。** 字幕が出ているフレームだけ通す手もあるが、
Canvasを経由すると色がYUV→RGB→YUVと往復するので、字幕の出入りで色がわずかに動く。
さらにCanvasの出力は「回転を起こしたあと」の寸法なので、素通しのフレームと食い違う。
どちらも画面に出てしまうため、通すなら全部通す。

**縦撮りの扱い。** スマホの縦動画はピクセルが横向きのまま「90度回して表示せよ」という
指示がmp4に入っている。字幕を入れないときはその指示ごと引き渡しているが、焼き込むときは
先にピクセルを起こしてから描き、指示のほうは付けない（付けると二重に回って横倒しになる）。
`test/subtitle-burn.js` に回転メタデータ付きの動画での回帰テストがある。

**書体はiOS標準のものだけ。** ウェブフォントを使うと、書き出し側（Worker内の
OffscreenCanvas）にも同じフォントを読み込ませる必要があり、オフラインで焼き込めなくなる。

**文字起こしはこのアプリで唯一ネットにつながる処理。** Whisperのモデルを
Hugging Face から一度だけダウンロードする（以降はブラウザのキャッシュ）。
ダウンロードするのはモデルだけで、動画も音声もアップロードしない。
**読み込むのは jsDelivr の `+esm` でなければならない。** 公式が配っている
`dist/transformers.web.js` は `import ... from "onnxruntime-web/webgpu"` という
名前だけのimportを含んだまま配布されていて、ブラウザはこれを解決できず、
読み込んだ瞬間に落ちる（実機で発覚）。バンドラを使う前提のファイルで、ビルド工程を
持たないこのアプリでは使えない。`+esm` は依存を解決した形を返すのでそちらを読む。
**exportされている関数を調べるだけでは、読み込めるかは分からなかった。**

**既定はWASM（CPU）で、WebGPUは自分からは選ばない。** WebGPUのほうが速いが、実機
（iPhone）ではタブごと落ちた。落ちると `try/catch` では掴めず、画面が読み込み直されて
開いていた動画まで消える。遅いほうがまだましなので、確実に動くWASMを既定にしている。
WASMで走らせるときは軽いほうの実行ファイル（14MB。既定の asyncify 版は27MB）を使う。
CPUだけで回すなら通常版で足り、13MB少ないぶんメモリで落ちる余地が減る
（手元の検証では速度も変わらなかった）。既定のモデルも小さいほう（tiny）にしてある。

**実行方法は先に1つだけ決める。** 「WebGPUで試して駄目ならWASM」という作りにすると、
同じワーカーの中では必ず失敗する。ONNX Runtime が推論セッションの作成を1本の
Promiseの鎖で直列化していて（`chain = chain.then(create)`）、一度失敗するとあとから
積んだ分も同じ失敗を受け継ぐため。しかも報告されるのは最初の失敗（WebGPU側）の
文言なので、WASMで落ちたように見えない。そこで **GPUが実際に取れるかを先に確かめて
1つだけ試し**、それでも駄目なときは **ワーカーごと作り直して** WASMでやり直す。

**幻聴（hallucination）を音量で落とす。** Whisperは声が無いところでも、それらしい
言葉を作る。日本語では「ご視聴ありがとうございました」などが典型で、無音部分に
勝手に現れる。決まり文句の一覧で消す手もあるが、本当にそう喋っている動画で
消えてしまうので採らない。代わりに、その時間に実際に音が入っていたかを測って
（-45dBを下回れば捨てる）判断する。文字起こしに渡した音声がそのまま手元にあるので
追加のデコードは要らない。

**分割はライブラリ任せにせず自前でやる。** ライブラリにも長い音声を分ける機能があるが、
使うには音声を丸ごと1本のFloat32Arrayに載せる必要があり、30分の動画だと100MBを超える。
自前で区間に切れば、常にメモリに載るのは30秒ぶん（約2MB）で済み、区間ごとに進捗も出せる。
**区切りは波形のRMSを見て一番静かなところに寄せる**ので、言葉の途中で切れにくい
（タイムラインのために解析済みの配列をそのまま使うので、デコードのやり直しは起きない）。

**中止はワーカーごと終了させる。** 推論の最中、ワーカーは1区間の計算が終わるまで
イベントループに戻らないので、中止フラグを送っても読みに来ない。

**編集できるのは再生位置に出ている1行だけ。** スマホの画面に何十行ものテキスト欄を
並べると重くて触りにくい。他の行は一覧から選んでその位置へ飛ぶ（＝編集対象が切り替わる）。

### 落ちたときにどうするか

重い処理の最中にブラウザがタブごと読み込み直すことがある（メモリ不足）。これは
`try/catch` では掴めない。画面はただ読み込み直されて、開いていた動画も消える。
実機の文字起こしでこれが起きた。対策は2つ。

**作業記録を残す。** 進んだところを都度 localStorage に書いておく（`core/breadcrumb.js`）。
次に起動したとき、終わっていない記録が残っていれば「前回ここで止まった」と出せる。
**落ちたときに手がかりを残せるのはこれだけ**なので、実行方法・モデル・版も一緒に残す。
ワーカーからは localStorage を触れないため、書くのは常に画面側（進捗を受けて記録する）。

**動画そのものを覚えておく。** `<input type=file>` で選んだファイルはページの寿命しか
生きていないので、読み込み直されると消える。編集内容は localStorage にあるのに動画だけ
無い、という状態になるため、IndexedDB に入れておいて開き直せるようにした
（`core/file-store.js`）。名前・大きさ・更新日時が同じなら保存済みの編集リストにも
当たるので、続きから再開できる。容量が足りなければ黙って諦める。

### フレームの並べ替え（Bフレーム）対策

H.264のエンコーダは圧縮効率のためフレームを溜めて並べ替えることがある。
並べ替えたフレームがキーフレームをまたぐと、表示順では前に来るフレームが
キーフレームより後から出てきて、mp4に詰める側の
「直前のキーフレーム時点の最大タイムスタンプより小さい値は入れられない」
という検査に引っかかり、書き出しが止まる（実機のSafari/H.264で発生）。

この検査が問題になるのは**エンコーダが自分の判断で差し込んだキーフレーム**のとき。
クリップの切れ目は映像が突然変わるので「シーンチェンジ」と見なされて自動挿入されやすく、
**クリップが増えるほど当たりやすい**（無音カットで21個・42個に分けたときに再発し、
2〜3個では出なかった）。

対策は3段構え:

1. **クリップの1フレーム目は明示的にキーフレームにする**（`{ keyFrame: true }`）。
   明示要求したキーフレームは、それより前のフレームを出し切ってから作られるので
   並べ替えが切れ目をまたがない。エンコーダが自前で挿す動機も無くなる。
   カット位置の画質が上がる副次効果もある。
2. `latencyMode: 'realtime'` で並べ替え自体を抑える。ただしこの設定は
   「詰まるとフレームを落とすことがある」とされているので、投入フレーム数と
   出力パケット数を数え、食い違ったら結果に「Nフレーム欠落」と出す。
3. それでも止まったら、**1フレームずつ `flush()` して出し切るエンコーダ**
   （`src/export/serial-encoder.js`）で1度だけやり直す。溜め込めないので
   並べ替えは起きようがない。遅くなるがPフレームは使えるのでサイズは普通のまま。
   やり直した場合は結果に「やり直し実行」と出る。

ヘッドレスChromiumのVP9ではBフレームが出ないため、**元の不具合はCIでは再現しない**。
テストで担保できるのは「細かいクリップでも時刻が巻き戻らないこと」と
「逃げ道のエンコーダが正しいmp4を作ること」まで。
