# スマホ完結の動画編集PWA

スマホのブラウザだけで完結する、個人利用の動画編集ツール。
サーバーを持たず、処理はすべて端末内で行い、静的ホスティングだけで配信できる。

**ステップ1（書き出しの検証）は実機（iPhone Safari）で確認済み。** H.264/AACの
エンコード・デコードとも対応、書き出し・音ズレなし・保存まで動作した。
ステップ2（トリム・ピンチズーム）、ステップ3（dB表示）、
ステップ4（音声エフェクトと無音の自動カット）まで実装済み。

## 今できること

| できること | 操作 |
| --- | --- |
| mp4を開く | 「ファイルを開く」 |
| 再生位置でカット | 「ここでカット」／スペースキー |
| クリップを出力から外す・戻す | クリップをタップ（選択中のものをもう一度タップ） |
| クリップごとの速度 | ×0.5 / 0.75 / 1 / 1.25 / 1.5 / 2 の6ボタン |
| クリップの端をトリム | 選択中クリップの端（白い縦線のハンドル）をドラッグ。隣のクリップの境界までしか動かせない |
| タイムラインをズーム | ピンチイン・ピンチアウト（指の中間点の時刻を保ったままズーム＋パンする） |
| ズームを解除 | タイムラインをダブルタップ |
| 画質を選んで書き出す | 高画質 / 標準 / 軽量（1080pで12 / 6 / 3Mbps相当） |
| 保存 | 共有シート（iOSはここから写真アプリへ）／ダウンロード |
| 編集の途中保存 | localStorage に自動保存。同じ動画を開き直すと続きから |
| タイムラインの波形 | 開くと自動で解析（Web Worker）。dBスケール（0〜-60dB）、-3dB超は列を赤く強調、ピーク＋RMSを重ねて描く |
| 再生中のdBメーター | プレビュー右の縦バー。RMS＋ピークホールド（1.1秒）、-0.6dBでCLIPランプ点灯 |
| 音の仕上げ | トグル5つ（音量をそろえる／声をはっきりさせる／ノイズを減らす／音割れを防ぐ／出だしと終わりをなめらかに）。専門用語は出さず、ONで効く |
| 無音の自動カット | しきい値（-50 / -45 / -38dB）を0.6秒以上下回る「間」を外し、音のあるところだけのクリップに分ける。「元に戻す」付き |

元ファイルは一切書き換えない。持っているのは「どこからどこまでを何倍速で再生するか」の
編集リストだけで、プレビューも書き出しもそれを読んで行う。

トリムは「選択中のクリップ自身の端」だけを動かせる。隣のクリップの領域には食い込めない
（両方の境界を一緒に動かす「リップル編集」はしない）ので、境界を詰めたいときは
両側のクリップをそれぞれ選び直して両方の端を動かす。

波形は音声トラックを区間ごとに分割デコードし、一定フレーム数ごとのピーク／RMSだけを
配列で保持する（全体をメモリに載せない）。ズームレベルが変わっても解析をやり直さず、
その配列を集約し直すだけで描く。dBメーターは別物で、`<video>` に挿したWeb Audioの
AnalyserNodeから再生中に毎フレーム読む。タイムラインの波形は左右チャンネルを合成した
1本だが、再生中のdBメーターはL/Rを2本のバーで別々に表示する。

音の仕上げは、プレビューではWeb Audioの標準ノード、書き出しでは同じ構成を組み直した
自前のDSP（`src/audio/dsp.js`）で処理する。書き出しはWeb Workerの中で走り、
Workerでは Web Audio API が使えないため。耳で確かめるのはプレビュー、
実際に出来上がるファイルを決めるのは書き出し側になる。

**接続順は仕様から1点だけ変えている。** 仕様は「…→リミッター→ゲイン→フェード」だが、
「音量をそろえる」のゲインは普通プラスの値になるため、リミッターの後ろに置くと
せっかく-1.5dBで抑えた音をまた押し上げてしまい、「音割れを防ぐ」というリミッター自身の
目的を打ち消す。そこでゲインだけ鎖の先頭へ移し、リミッターを最終段にしている。

まだ無いもの: 字幕、映像フィルター、マーカー、
PWA化（Service Worker）、ffmpeg.wasm フォールバック。これらはステップ5以降。

## 実機で確かめてほしいこと

WebCodecs は **https か localhost でしか動かない**ので、スマホで試すには
どこかに置く必要がある。いちばん手軽なのは Cloudflare Pages。

```
# Cloudflare Pages（ビルド不要・出力ディレクトリはリポジトリ直下）
#   Framework preset : None
#   Build command    : （空）
#   Output directory : /
```

開いたら、画面いちばん下の **「この端末の対応状況」** を見る。

1. `映像を書く（H.264エンコード）` が **対応** になっているか
2. 30秒くらいのmp4を開いて、カットと速度変更をして「書き出す」が通るか
3. 出来上がった動画をその場のプレビューで再生して、**音と映像がずれていないか**
4. 「保存・共有」から写真アプリに入れられるか
5. 書き出しに何秒かかったか（30秒の動画で何秒か）

うまくいかないときは「結果をコピー」でUser Agentと対応状況をコピーできる。
それを貼ってもらえれば原因を絞れる。

→ **iPhone Safari（iOS 18.7）で確認済み。** 判定は `ok`（H.264/AACとも対応）、
書き出し後の音ズレなし、ダウンロード保存も成功。

### 手元で動かす

```
npm install     # テストを走らせる場合のみ。アプリ本体はビルド不要
npm run dev     # http://localhost:5173
```

## テスト

```
npm test            # 下の2つを両方
npm run test:unit   # 編集リスト・リサンプラ・ビットレート・タイムライン座標計算（Node）
npm run test:browser # 書き出し・タイムライン操作・波形解析・音の仕上げ（ヘッドレスChromium）
```

`test:browser` は、1秒ごとに色が変わり秒ごとに音量も変わる12秒のテスト動画を
ブラウザ内で作り、3つの観点で確かめる。

1. カット・除外・速度変更を指定して書き出し、**出来上がった動画をデコードし直して
   「出力の何秒目に元動画の何秒目のフレームが来ているか」を色で確かめる。**
   音声と映像の長さのずれも見る。
2. タイムラインに実際の PointerEvent（タップ・ドラッグ・2本指ピンチ・ダブルタップ）を
   送り、シーク・ズーム・トリムが正しく発火するか（`test/timeline-interaction.js`）。
3. 音声を解析し、テスト動画の「大きい→標準→小さい→無音」の4区間それぞれで
   検出したdBが理論値に近いか、-3dBを超える区間だけが「音割れ危険」判定になるか
   （`test/waveform-analysis.js`）。
4. 音の仕上げをONにして書き出し、**出来上がったmp4をデコードし直して**
   リミッターが上限で止めているか、音量をそろえるとピークが-3dBに寄るか、
   フェードで頭と尻が絞れているか、無音カットで実際に短くなるか
   （`test/audio-effects.js`）。

ヘッドレスChromiumはオープンソースビルドなので H.264 / AAC を持たない。
そのためテストだけは同じmp4コンテナのまま VP9 / Opus に差し替えて走らせている
（`runExport` の `codecs` 引数）。**つまり「パイプラインの論理」はCIで担保できるが、
「H.264/AACが実際に通るか」は実機でしか確認できない。** ステップ1でその点は
実機（iPhone Safari）で確認済み。

ビルド工程なし。ブラウザがそのまま読めるESモジュールだけで書いてある。

```

  main.js                画面とデータの配線
  core/
    edit-list.js         編集リスト本体。カット・除外・速度・トリム・保存
    capabilities.js      端末の機能判定（WebCodecs / H.264 / AAC …）
    codecs.js            書き出しコーデック（テストで差し替える一点）
    save-file.js         共有シート／ダウンロード
    wake-lock.js         書き出し中に画面を消させない
    format.js            時間・バイト数の表示
  export/
    controller.js        ワーカーの起動と進捗。ワーカー不可ならメインスレッドで実行
    worker.js            ワーカーの入口
    pipeline.js          demux → デコード → 時刻の振り直し → エンコード → mux
    resampler.js         速度変更ぶんの音声リサンプル（逐次処理）
    quality.js           高画質/標準/軽量 のビットレート
  audio/
    dbscale.js           dB変換・グリッド・集約の純粋関数（DOM非依存、ユニットテスト対象）
    dsp.js               書き出し用のエフェクト実装（フィルター・コンプ・ゲイン・フェード）
    effects.js           5つのトグルの対応表と、書き出し用エフェクト鎖の組み立て

    preview-audio.js     プレビュー用のWeb Audioグラフ（エフェクト＋メーターのタップ）
    waveform.js          区間ごとに分割デコードしてピーク/RMS配列を作る（Worker/メイン共用）
    waveform-worker.js   波形解析ワーカーの入口

  ui/
    player.js            クリップ順に再生位置を飛ばすプレビュー
```

### 編集データ形式

これだけを保持し、localStorage に入れる。`id` と `enabled` は
UIがクリップを指すため／「除外しても削除はしない」ために足した2つ。

```json
{
  "source": "IMG_0431.mp4",
  "clips": [
    { "id": "c1", "in": 0.0, "out": 12.4, "speed": 1, "enabled": true,
      "filter": { "brightness": 1.05, "contrast": 1.15, "saturation": 1.3, "hue": -8, "vignette": 0 } },
    { "id": "c2", "in": 18.9, "out": 47.2, "speed": 1.5, "enabled": true, "filter": null }
  ],
  "audio": {
    "normalize": true, "normalizeGainDb": 4.2,
    "clarity": true,
    "highpassHz": 110,
    "limiterDb": -1.5,
    "fade": true
  },
  "markers": [ { "t": 24.0, "label": "要確認" } ]
}
```

`audio` は仕様の3つ（`normalizeGainDb` / `highpassHz` / `limiterDb`）をそのまま残しつつ、
数値を持たないトグル（声をはっきりさせる・出だしと終わりをなめらかに）のON/OFFを足してある。
`highpassHz: 0` と `limiterDb: null` がそれぞれ「ノイズを減らす」「音割れを防ぐ」のOFFを表す。
`normalizeGainDb` は波形から自動計算して入る値なので、画面から直接は触らない。

`filter` と `markers` はまだ読み書きしないが、後のステップでそのまま使えるよう
場所だけ確保してある。

### 当初の技術構成からの変更点

書き出しに mp4-muxer + mp4box.js を使う想定だったが、**mp4-muxer は作者自身が
非推奨とし、後継の Mediabunny へ移行するよう案内している。**
Mediabunny は同じ作者による後継で、mux と demux の両方を担当するため
mp4box.js も不要になる。加えて、

- ファイルを `Blob.slice()` で遅延読み込みする（mp4box.js は解析前に全体を
  メモリへ載せる必要があり、30分のスマホ動画ではタブが落ちる）
- `EncodedPacketSink` があるので、後のステップで「フィルターも速度変更もない
  クリップを再エンコードせず通す」無劣化パススルーを素直に実装できる

という2点が、長尺対応とメモリの要件に直接効く。詳細は `vendor/README.md`。

### 現時点で残している既知の課題

- **書き出し結果をメモリ上に一度組み立てている**（`BufferTarget`）。30秒なら問題ないが、
  長尺では `StreamTarget` + File System Access へ切り替える。フレーム自体は
  すでに逐次処理なので、差し替えるのは出力先だけ。
- **全クリップを再エンコードしている。** 無劣化パススルーはステップ6で入れる。
- **WebCodecsが無い端末のフォールバック（ffmpeg.wasm）が未実装。** いまは
  「対応状況」に理由を出して書き出しボタンを止めるところまで。
- **トリムは選択中クリップの端だけを動かせる。** 隣のクリップの端を同時に動かす
  「リップル編集」はしない（データ上は各クリップが独立して in/out を持つ設計のため）。
  境界を詰めたいときは両側をそれぞれ選び直してトリムする。
- **タイムラインの波形は左右チャンネルを合成した1本。** ステレオ感を見たい場合は
  再生中のdBメーター（L/Rを別バーで表示）の方を見る。
- **波形は毎フレーム、画面の列ごとに集約し直して描いている。** 長尺で極端に
  ズームアウトしたときの負荷はステップ9の負荷試験で確認する。
- **プレビューと書き出しでエフェクトの実装が別。** 数値（しきい値や周波数）は
  `EFFECT_PARAMS` で共有しているが、コンプレッサーの内部挙動はブラウザ実装と
  自前実装で完全一致はしない。最終的な音を決めるのは書き出し側。
- **プレビューにフェードは入れていない。** 書き出したファイルの頭と尻の話なので、
  プレビュー再生では省いている。
- **無音の自動カットはクリップ一覧を作り直す。** 速度や除外の指定は消えるので、
  直後だけ「元に戻す」で戻せるようにしてある。
- **映像エンコーダは `latencyMode: 'realtime'` で動かしている。** 既定の `'quality'` だと
  エンコーダがキーフレームをまたいで参照するフレーム（Bフレーム）を出すことがあり、
  mp4に詰める側の「直前のキーフレーム時点の最大タイムスタンプより小さい値は入れられない」
  という検査に引っかかって書き出しが止まる（実機のSafari/H.264で発生）。
  `'realtime'` は詰まるとフレームを落としうるので、投入フレーム数と出力パケット数を
  数えて、食い違ったら書き出し結果に「Nフレーム欠落」と表示する。
  ヘッドレスChromiumのVP9ではBフレームが出ないため、この不具合はCIでは再現しない。
